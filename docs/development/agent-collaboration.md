# Agent 协作与执行规则

更新时间：2026-09-12

用途：承接 `AGENTS.md` / `CLAUDE.md` 不适合在每次任务启动时全量加载的协作细则。

读者：仓库维护者、人工协作者与 AI / Agent。

不包含：当前阶段计划、临时门禁、功能设计正文、命令级历史流水或发布记录。

## 文档职责与优先级

### 三层职责

| 层级 | 职责 | 典型内容 |
| --- | --- | --- |
| 根协作入口 | Agent 启动即生效的长期契约 | 授权边界、协作原则、核心红线、任务路由 |
| `docs/` 稳定专题 | 按任务读取的详细规则与契约 | 架构、接口、代码风格、验证方法、协作流程 |
| 当前状态与记录 | 会随阶段变化的状态和事实 | 当前优先级、临时门禁、“当前不做”、批次证据 |

`AGENTS.md` / `CLAUDE.md` 不是项目手册的副本，`docs/README.md` 也不是阶段规则正文。根入口负责说明“启动时必须遵守什么、下一步去哪里读”，专题文档解释稳定规则，`docs/status/current.md` 说明当前状态，周志和历史材料记录已经发生的事实。

### 判断顺序

1. 先遵循项目所有者在当前任务中的明确要求。
2. 再遵循 `AGENTS.md` / `CLAUDE.md` 的启动级约束。
3. 根据任务路由读取当前 `docs/` 真相源。
4. 通过代码、测试、配置和验证结果确认实现事实。
5. 文档与实现冲突时，先判断哪一侧过期，再在当前任务范围内统一口径。

## 任务推进流程

### 开始任务

- 先检查工作区状态，避免覆盖用户或其他协作者已有改动。
- 判断请求属于回答、诊断、设计、实现、验证、发布还是等待；不从只读请求推导出范围外写入。
- 只读取任务路由要求的最少文档；需要追溯依据时再进入周志、验收记录、release 草案或历史文档。
- 涉及当前状态、优先级或下一步时先读 `docs/status/current.md`；进入具体功能时再读 `docs/topics/README.md` 和对应专题。

### 方案与批准

- 用户未明确要求直接修改时，写代码前说明目标、边界、影响和验证方式，并等待批准。
- 架构、规则、接口、依赖、运行时行为、阶段边界或验证基线的变化，即使用户要求修改，也应先说明可能影响并确认范围。
- 不同合理解释会造成明显不同的用户行为、数据模型、兼容边界或外部影响时，先澄清再修改。
- 已批准方案出现实质性范围变化时，暂停扩张并重新确认，不把变化隐藏在实现细节中。

### 实现与收口

- 优先治理根因和同类问题，避免只修一个表象后留下重复缺陷。
- 交付覆盖真实需求和主要路径，不使用占位逻辑、玩具式实现或无法验证的半成品。
- 不做与目标无关的重构；直接影响需求的结构问题可以做边界清楚的必要修正。
- 抽象必须服务真实复用、边界隔离、复杂度下降、领域表达或契约稳定。
- 错误处理只覆盖明确的输入、IO、网络、权限、并发和兼容风险；不吞异常、不伪造成功、不用默认值掩盖契约问题。
- PR 合并到 `master` / `main` 后，必须按分支治理 ADR 把最新稳定主线回灌并推送到 `dev`；确认远端拓扑收口前不开始下一轮开发，也不把任务描述为完整收口。
- 交付时说明完成内容、验证结果和仍未验证的真实风险，不把未执行的运行态检查描述为通过。

## 操作授权与环境边界

### 直接执行范围

- 用户已经要求修改时，可进行任务范围内的代码、文档和配置读写。
- 可执行与改动直接相关的构建、测试、格式检查、Lint、静态分析和仓库治理检查。
- 可执行只读 Git 操作；范围清楚且验证完成时，可按用户要求进行常规提交。

### 先告知再执行

- 启动桌面 UI、`cargo run` 或其他长时间、交互式进程前，说明命令、运行影响和清理方式。
- COM 注册或反注册、安装证书、写系统注册表等环境修改必须说明目标、风险和回滚方式。
- `cargo add`、`cargo update`、`dotnet add package`、需要联网的 restore 等依赖操作必须说明包、版本及 lockfile 影响。
- 打包、发布、安装和真实 PME / Windows smoke 必须说明产物、环境影响和验证边界。
- 授权只覆盖当前任务中已经说明的命令和范围；命令、依赖或影响发生实质变化时重新确认。

### 沙盒与真实环境

- 构建、测试和最小验证默认先在当前沙盒内执行。
- 若失败明显来自权限隔离、受限 restore、project reference 解析、native 加载路径、证书或系统环境差异，可在告知用户后申请最小范围真实环境复验。
- 提权或真实环境复验不扩大任务授权；依赖变更、服务启动、注册、打包和发布仍必须单独说明。
- 不通过修改代码或增加 fallback 来掩盖已经确认的环境性失败。

## 文档归位规则

| 内容 | 真相源 |
| --- | --- |
| 当前维护状态、优先级、临时门禁、“当前不做” | `docs/status/current.md` |
| 功能或开发目标的范围、阶段、验收和验证 | `docs/topics/` 与 `docs/mvp/` |
| 架构、模块职责和跨层边界 | `docs/architecture/`、`docs/capeopen/`、`docs/thermo/` |
| 命名、抽象和语言实现规范 | `docs/development/code-style.md` |
| Agent 任务流程、授权和验证选择 | 本文档 |
| 分支、PR、版本等重要治理决策 | `docs/adr/` 与对应架构文档 |
| 当前结论的历史过程和验证证据 | `docs/devlogs/`、验收记录或 release 记录 |
| 文档分类、索引、篇幅和维护方式 | `docs/README.md` |

维护文档时遵循以下规则：

- 优先更新已有真相源，不为一次性讨论创建散文档。
- 总体状态只承载阶段、优先级和下一步；具体功能细节进入对应专题。
- 架构、接口、项目格式、流程或阶段边界变化时，先更新对应专题，再同步当前状态摘要和周志。
- 历史过程、命令输出和验证流水不堆入根入口或文档索引。
- 每篇新增或大改文档在开头说明用途、读者和不包含内容。
- 篇幅、拆分和索引规则以 `docs/README.md` 为准。

## 实现质量原则

### 需求与范围

- 先保证需求完整正确，再保证架构边界清晰，然后控制修改范围和复杂度，最后按风险选择验证。
- 不为单次需求预先扩展无关能力；每个新增文件、类型、变量和函数都应有明确用途。
- 不把“修改最少”凌驾于正确性和长期一致性，也不借完整治理扩大到无关重构。

### 可读性与抽象

- 代码应让不熟悉当前改动的开发者能顺着领域流程读懂。
- 优先使用命名清晰的普通函数、早返回和顺序流程；避免影响阅读的函数嵌套和回调嵌套。
- 不新增只有技术包装意义的 helper、manager、orchestrator、context 或 adapter；确需使用时，名称必须表达具体领域边界。
- 源码接近仓库行数阈值时按真实职责拆分，不做机械切片或纯转发模块。

### 错误与兜底

- 对外部输入、IO、网络、权限、并发和互操作边界做必要校验并保留可诊断上下文。
- fallback 必须对应明确的兼容或恢复场景，不能隐藏数据模型、契约或状态机错误。
- Rust 优先用类型系统、`Result` / `Option`、所有权和结构化错误表达约束；C# / `.NET` 保持 COM 语义在适配层内闭合。

## 验证与留痕

- 每完成一个可分割步骤先做定向验证，再根据影响面决定是否扩大到 crate、workspace 或仓库级基线。
- 文档与治理改动至少检查协作文件同步、Markdown 相对链接、文本格式、文档体量和 `git diff --check`。
- Rust 核心、公共模型、求解、存储或项目格式变化应执行相关测试；跨 crate 或阶段收口时回到正式 `check-repo` 入口。
- `.NET 10` CAPE-OPEN 解决方案、native 装载和 PME smoke 按对应专题在合适环境验证，不用沙盒假阳性或假阴性替代最终结论。
- 当前正式命令、阶段附加门禁和最近通过记录只在 `docs/status/current.md` 维护，不复制到根入口。
- 本周重要推进写入 `docs/devlogs/YYYY-MM/YYYY-Www.md`；记录目标、完成情况、关键决策、风险与未完成项、下周建议。

### Rust 工具链与锁定依赖

- `Cargo.toml` 的 workspace `rust-version` 声明仓库选择支持的最低 Rust 版本；它不是对“理论上最老能编译的版本”的探测结果。未在候选低版本运行完整验证前，不下调声明或承诺兼容。
- `rust-toolchain.toml` 固定日常验证工具链到具体补丁版本；`PR Checks` 与 `Release Checks` 中所有 Rust setup 使用同一版本。当前数值和验证证据见 [当前状态](../status/current.md)。本机可用 `rustup show active-toolchain` 排查环境变量或目录 override，不能只凭配置文件判断实际运行版本。
- 正式 Rust 构建、测试、clippy 和 CI 的 `xtask` 入口使用 `--locked`，锁文件需要变化时直接失败；该选项允许下载已有锁定版本，不等于离线。依赖缓存齐全时可设置 `CARGO_NET_OFFLINE=true` 复验。
- `.github/workflows/rust-compatibility.yml` 仅由 `workflow_dispatch` 手动触发，在 Linux、macOS、Windows 上运行浮动 `stable` 的 `check-repo`；job 显式设置 `RUSTUP_TOOLCHAIN=stable`，让子命令也使用待评估工具链。它不进入 `Candidate Quality`，不自动更新基线、依赖或产物。
- 维护工具链时，先用 `cargo metadata --locked --format-version 1` 核对锁定依赖及 `rust_version`，再在选定版本执行正式检查。依赖声明的最高版本只是下界线索；缺失声明、目标平台、features 和源码使用的语言特性都可能影响实际兼容性。
- 更新固定版本时，同步工具链文件、两个正式 workflow 和必要的最低版本声明；先通过本机正式基线，再通过对应 CI 验证其他平台。记录未执行的平台和运行态检查，不用 macOS 成功替代 Windows / Linux 或 `.NET` / COM 验证。
- 固定 Rust 和 `Cargo.lock` 用于复现编译器与 Rust 依赖组合；CI runner 镜像、系统库、Actions 引用和 `.NET` SDK 未全部固定，因此不承诺逐字节一致的构建产物。

字段与工具行为参考 [Cargo rust-version](https://doc.rust-lang.org/cargo/reference/rust-version.html) 和 [Rust toolchain Action](https://github.com/dtolnay/rust-toolchain)。

## 根协作入口维护

一条规则只有同时满足以下条件，才应加入 `AGENTS.md` / `CLAUDE.md`：

1. 跨任务成立，而不是某个功能或批次专属。
2. 跨开发阶段成立，不会随当前里程碑自然失效。
3. 必须在 Agent 读取专题文档前生效，否则容易造成高风险或大范围错误。
4. 无法只通过任务路由和对应 `docs/` 专题可靠承载。

不满足这些条件的内容应归入稳定专题、当前状态、记录或归档。两份根入口必须全文一致；修改时同步检查关联文档仍为真相源，并执行仓库治理检查。
