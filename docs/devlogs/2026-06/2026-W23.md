## 关键决策

- 旧 `SolveSnapshot` 只保留为历史和 stale notice 来源，不成为第二套结果真相源。
- Results commands、轻量复制 / 导出、Result Inspector、底部结果表和 review summary 只消费当前 revision 的 latest snapshot。
- 编辑后旧结果失效属于建模正确性表达，不进入跨快照报表、差异比较或完整历史结果管理。
- `Resume` 是用户可触发的运行入口，不能因为它来自 Hold/pending 状态就绕过 readiness；`Recover failure` 命令本身仍只执行失败恢复动作，恢复后若产生新的 Feed source stream 输入缺口，后续 Resume 继续由 readiness 引导补齐。
- readiness 的单一判断源放在 GUI shell 之下、求解派发之前；物性包解析仍先走正式 run package resolution，结构性连接、拓扑、非法旧项目和求解阶段参数失败仍交给 Run Panel 诊断 / recovery。
- 通用小流程建模 v1 已满足当前用户主路径要求；后续不继续用同类 Inspector / readiness / 作者入口回归消耗主线，只在真实 blocker、结果判断缺口或事实源冲突出现时回到该阶段修正。
- Studio UI 专题进入设计前置阶段，设计稿、端点边界和状态模型先行；代码实现必须继续沿用 presentation / command / state 边界。
- 首批设计端点按 P0 / P1 / P2 分层推进：P0 `studio-client-main.pen` 先统一 Studio 客户端本体主工作流，P1 只在需要时创建窄口径 `module-settings-panel.pen` 细化模块设置 / 结果，不再维护完整 Workbench 复制稿；P2 控制面和只读端点只做边界，不提前扩完整后台或移动端编辑能力。
- Pencil app 不可用时，不用普通文件工具伪造 `.pen`；后续 `.pen` 继续通过 Pencil 创建、维护和验证，仓库内只做文件搬移、命名、提交和文档同步。
- P0 后续视觉方向以 `baseline/radishflow-home-dashboard-concept-v2-20260516.png` 和 `baseline/radishflow-workbench-concept.png` 为 RadishFlow 自身基线；其他同目录截图只作为参考素材或历史对照。
- P0 信息架构评审通过只代表可以进入 P1 设计准备，不代表可以跳过 P1 或直接进入 UI 代码实现；代码实现前仍需确认 P0 / P1 设计稿、状态来源和允许偏离点。
- 物性是流程模拟软件的核心工作区，长期需要组分查询、项目组分、方法选择、参数调整、交互参数、数据来源、公式展示和物性分析；因此当前设计把 `物性` 提升为顶部导航下的独立页面，而不是左侧或右侧栏 tab。
- 模块设置 / 模块结果先作为 `studio-client-main.pen` 内的右侧栏或画布标签页结构处理，不把 Feed、Mixer、Heater / Cooler、Valve、Flash Drum 做成互相独立的整页 UI；当前稿仍不包含完整参数表、自由连线、完整报表或未来高级模型配置。
