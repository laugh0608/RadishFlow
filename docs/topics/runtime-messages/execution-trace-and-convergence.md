# 执行追踪与收敛诊断

更新时间：2026-11-25

## 用途与状态

用途：维护真实执行过程、嵌套迭代和采集能力边界。
读者：求解器、运行事件和收敛视图维护者。
不包含：新求解算法、完整性能指标、重启检查点实现。

- 层级：二级功能；父专题为 [运行、消息与诊断](../runtime-messages-and-diagnostics.md)。
- 状态：N2 无回路稳态运行后审阅已接通。循环、实时观察和持久化按各自切片推进。
- 范围、依赖与 N0—N5 顺序以父专题为准；[需求追踪表](requirements-traceability.md) 记录要求、阶段、场景及证据。

## 当前基础与用户路径

现有 `SolveSnapshot` / `StepSnapshot` 可复用成功步骤证据，但不能代替开始、失败和终止事件。用户从运行进入执行树，选中步骤查看诊断；循环能力到位后查看对应层级残差，再定位实际变量。

## 执行追踪与收敛观察

执行树由实际运行计划产生：运行→检查→执行组 / 循环→迭代→设备或方程求解→结果校验。单元可以重复执行；设备树、画布树和求解树不要求同构。EO、黑箱和并行执行只暴露所支持粒度，不能强制伪造成按设备串行。

节点按能力提供状态、耗时、工况、输入 / 输出观察值、残差、容差、归一化定义、相关事件与监视入口。现有顺序求解先记录真实步骤，不填虚构迭代数、进度百分比或剩余时间。失败步骤也应留下开始、失败位置及已知上下文，不能只有成功快照才有过程证据。

收敛曲线明确循环 / 内外层、迭代坐标及残差缩放；不同物理量的原始数值不直接比较严重程度。未来显示最难收敛变量和停滞 / 振荡时，必须给判据及适用层级；无判据不把趋势外观当数值结论。

简要 / 正常 / 详细显示与采集级别分开。运行前明确采集范围，事后不能凭空恢复未采集数据。内存有界、界面批量刷新、普通高频 trace 可采样；错误、停止命中、恢复和终止证据不能被静默丢弃。容量或记录失败须报告截断 / 丢失范围，不反过来改变物理求解结论；无记录时不承诺完整复现。

## 事件顺序与观察边界

- 步骤开始与终止记录配对；失败后未进入的步骤显示“未执行”，不伪造开始 / 耗时。重试保留独立尝试身份，与同一对象多次执行区分。
- 事件保留运行内顺序和因果 / 父子关联；未来并行只承诺已知顺序，不靠墙钟排序制造不存在的先后关系。接收重复、迟到、缺段时须有明确处理策略，不重复计数或吞掉缺口。
- 观察值携带变量、单位语义、输入身份、试算 / 接受值及采集位置。残差缺失表示未采集 / 不支持，不能补零；耗时基准与未来仿真时间分别定义。
- 采集和显示订阅有各自容量边界。慢视图不能无限撑大运行内存；关键证据的记录失败应可见。具体背压、落盘和采样策略在 N2 决策，当前不承诺无损无限记录。

算法步长、导数检查、模型调用上下文与结构化大载荷见 [开发者诊断](developer-diagnostics-and-model-validation.md)。它们复用本专题的层级、采集与容量边界；可能增加模型求值的检查作为独立实验，不能暗改正式求解。

- D-02：N2 实施前定义事件粒度、运行内序号、重复 / 迟到 / 缺段策略、缓冲上限、背压、记录失败处置和采集档位；容量目标选实际负载测量。

## D-02 审阅提案：稳态运行记录（2026-11-25）

项目所有者已认可 D-02 与 D-07 局部交互。首批接通 Studio 后台 `Acyclic` 稳态计划的运行后审阅。M3 等方法沿用正式报告，循环迭代与残差按 D-03 推进。计算过程限当前工程会话，跨会话保存按 D-08 审定。 [局部评审包](../../architecture/designs/reviews/2026-11-25-studio-n2-execution-trace/README.md)

### 事实来源与运行身份

- [序贯求解器](../../../crates/rf-solver/src/lib.rs) 产生校验、正式执行顺序和真实单元调用事实。现有 [控制检查点](../../../crates/rf-solver/src/control.rs) 继续服务取消和最新进度。`UnitStarted` 检查点在设备求值之前，返回停止时设备尚未执行。`UnitCompleted` 检查点在输出已交付之后，即使此时取消，该步也已完成。记录应使用检查点与实际执行之间的边界，保留原取消时机和错误传播。
- [运行所有者](../../../apps/radishflow-studio/src/workspace_run_owner/mod.rs) 负责已受理的运行、记录收藏与结果接收。按既有 `FlowRunId` 归属，捕获文档会话、修订和已应用计划身份，实际装配后补包身份与指纹。未受理的点击保留原回执，重跑使用新的 `FlowRunId`。界面使用已有的运行显示编号。
- 运行记录、工作线程终态、结果接收处置和当前结果资格各自表达。只在当前结果确实来自选中运行时提供「查看结果」。旧输入或旧会话的运行可按保留和会话规则审阅，其执行结论不参与发布当前结果，也不会清掉其他运行的结果。 [一次性接收](../../../crates/rf-ui/src/flow_run.rs)

### 采集、顺序与容量

| 记录 | 采集位置与呈现 |
| --- | --- |
| 运行受理、准备、开始 | 应用层记录受理和实际获准开始。准备失败、开始前取消及授权拒绝保留原因，步骤区显示未进入求解。 |
| 顺序确定 | 求解器在检查通过后报告实际单元顺序和总步数。以计划序号区分步骤实例，稳定设备 ID 供定位。同一对象可在后续方法中对应多个步骤。 |
| 步骤开始与完成 | 在取消检查允许继续、进入单元步骤后记录开始。实际输出物化并交付求解器后记录完成，再检查下一次取消。耗时用单调时钟，可用时记录实际消费、产出的流股 ID。 |
| 步骤失败或执行中断 | 在已开始的步骤边界上保留下层结构化 `RfError`。准备、拓扑失败发生在计划之前时归运行级。发生线程中断且未取得步骤终态时显示「执行中断」，保留已知开始位置。 |
| 工作终态与接收处置 | 应用所有者消费真实终态及接收回执后封存记录。分开保存已返回、失败、取消、执行异常及是否接收。结构化诊断随原归属展示。 |

- 事件从实际产生端分配运行内严格递增序号。编号仅在同一运行比较。每个记录有一个写入者，封存后只读。当前进度继续使用已有合并槽，结束通过已有一次性完成通道交回记录。采集器保留在捕获线程异常的边界之外，使已采集前缀随线程异常一并交回。若完成载荷未送达，由运行所有者保留已知终态并标明记录缺失。UI 无须逐条消费，记录采集无额外取消点。重复回执沿用现有接收门禁。
- 默认记录运行阶段、计划、步骤状态、对象引用和终态。步骤详情引用有界结构化诊断和有资格的结果，记录本身保留来源与身份。术语和 SI 口径沿用现有契约，未采集值明确显示缺少依据。
- 单次最多 512 条计划行、2,048 条普通明细，N2 新增拥有载荷预算为 512 KiB，含 16 KiB 预留给物性包身份、终态、接收、截断及关键诊断。触顶后停止收集普通前缀，保留首个缺段序号、省略数量及实际失败步骤。过长的可选文本和目标信息报告缺失。沿用一个活动运行和最近八条摘要的保留上限，记录与摘要一同驱逐。采集失败只影响记录完整性。
- 在已确认计划中，终态明确留下的未开始后续步骤可标「未执行」。不可见计划尾部和缺证据步骤标「记录缺失」，保留已采集的真实失败点。准备前未执行、旧版会话未采集与已触顶是不同空状态。

### 验证与进入条件

1. 用空白双进料 Mixer 跑正常与第二股缺乙烷的案例，核对第二步开始／失败、第三步未执行、`stream-feed-2-outlet` 定位及修复后新运行。取消覆盖开始前、步骤边界和最后一步完成后，保留全部已确认完成的步骤。现有结果和执行终态分别判定。
2. 注入异会话、迟到、缺段、容量到顶和终态载荷断开，覆盖 AF3 已有的 10,000 次合并进度及连续 100 次运行基线。用可重复的大型无回路计划比较采集开关的运行耗时和载荷，并用 M3 验证按各自方法保留正式报告。 [AF3 基线与场景](scenarios-and-acceptance.md#n2-执行过程验收提案)
3. 交互先评审底部入口、失败定位／返回、窄区键盘及旧结果。产品接线后在 macOS 原生窗口验收，配合全仓和现有 CLI／FFI 兼容性回归。D-02 决议和局部交互认可归各自专题，验证状态按 [需求追踪表](requirements-traceability.md#n2-评审进展2026-11-25) 更新。
