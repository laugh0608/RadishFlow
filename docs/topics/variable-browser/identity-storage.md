# VB-D02 对象创建标识存储与迁移评审稿

更新时间：2026-11-12

## 用途与状态

本稿供项目所有者与 Studio、`rf-store` 维护者评审工程文件、显式初始化、旧版读写保护和失败恢复。对象引用规则、持久创建标识及旧工程由用户显式初始化已认可。本稿中的存储和兼容细节待评审。引用文本语法与浏览器交互见 [VB-D02 引用契约](stable-references.md)，关注项和外部协议分别归 VB-D03 与 VB3。

## 工程格式

建议沿用 `.rfproj.json`、外层 `schemaVersion: 4` 和 `document.metadata.schemaVersion: 1`，增加必需能力 `radishflow.object-identity` v1 和同层 `objectIdentities` 区。标识与对象图写入同一个工程文件，随另存和文件复制继承。`UnitId`、`StreamId`、工程设备记录、已有连接和求解计划仍用原有身份。v1 仅登记所有在存的流程单元和流股，包括尚未连通的对象。

以下为增量字段示例。完整工程仍含原 v4 必填区，能力列表由 writer 从实际工程推导。

```json
{
  "requiredCapabilities": [
    { "id": "radishflow.flow-plan", "version": 1 },
    { "id": "radishflow.object-identity", "version": 1 }
  ],
  "objectIdentities": {
    "units": [
      { "objectId": "heater-1", "creationId": "b91c614d-4a7a-4d0e-82ba-09c82da255ba" }
    ],
    "streams": [
      { "objectId": "stream-heater-1-out", "creationId": "3a66ed8a-4f0b-4b12-90c7-8fb945d24602" }
    ]
  }
}
```

- `objectIdentities` 与能力声明同时存在或同时缺省。启用后两个数组必填，可为空。空工程或删除全部对象后仍保留该能力。已知 v1 的缺字段、显式 `null`、未知字段、重复键、重复对象 ID、跨数组重复创建标识、缺记录、孤儿记录及非规范创建标识均是格式错误。检查按对象类型及原始 ID 精确匹配。writer 按数组内对象 ID 排序。
- 创建标识采用小写连字符 UUID v4 文本，分配使用系统随机源。分支各自独立分配，创建标识与名称、时间、文件内容、修订和顺序无关。碰撞时重取，随机源失败时取消整个准备或创建事务。存储解码只恢复已写标识，缺失或损坏时给出明确错误。
- 启用后，创建对象与分配标识同一事务。编辑、连接现有对象、撤销或重做保留原对象的标识。删除后，在当前会话内为可恢复的历史对象保留标识。文件只写在存对象，重开后若分配器重用旧对象 ID，生成的新标识会拒绝旧引用。初始化前就存在于本会话 Undo / Redo 中的对象一并分配会话内标识，撤销恢复时继承该标识，下一次保存才写入恢复对象。关闭和重开沿现有历史生命周期。
- 新增对象或撤销恢复的对象，只有当当前文件的最近成功保存已包含该标识时，才可新复制稳定引用。已存在的引用按当前会话对象解析，结果值继续由原资格门禁决定。来源能力随整个工程的保存基线记录，身份表随对象事务维护，不改变求解输入的定义。

选择 v4 的依据是已存在未知能力探测与整份原文只读路径。v4 的 `simulation.steadyStatePlan` 仍必填。v1–v3 迁移写入工作区原有的默认 `Acyclic` 配置，已有 v4 保存其实际计划。目标 v4 校验不通过时拒绝迁移，并指出具体对象或字段。保持模型、SI 值、来源、呈现和设备输入完整。 [现有 v4 codec](../../../crates/rf-store/src/project_v4/mod.rs) · [v4 文档校验](../../../crates/rf-store/src/project_v4/document.rs) · [默认执行计划](../../../crates/rf-ui/src/flow_plan.rs)

## 显式初始化与安全保存

建议无身份区的新工程与既有工程都沿用当前普通保存版本选择。用户第一次需要稳定引用时，执行 **启用稳定引用并保存**。未命名工程先选路径。已保存工程可选择新副本或原位升级，默认提供新副本。普通打开、运行、保存、另存和浏览不触发初始化。两份旧副本分别启用时独立分配标识。需要继承同一身份的副本应从已启用且成功保存的文件复制。

1. **准备。** 在活动可编辑工作区捕获会话、正式工程内容、草稿状态、来源路径及已保存版本和能力。为当前对象及可恢复历史对象准备标识，序列化完整候选文件，校验 v4 并读取实际目标版本、能力及原字节指纹。初始化可以保存到新路径或经现有覆盖确认替换已知未初始化的目标。已初始化、只读、未知或损坏的目标不接受此初始化写入。当前对象、路径和已保存状态此时仍按原工作区处理。
2. **确认。** 展示目标路径、是否覆盖、v1–v3 升至 v4 或 v4 新增能力，以及旧 Studio / CLI 的实际限制。明确会一并保存已提交的工程更改，草稿留在原编辑器。确认绑定同一准备记录。期间切换工程、输入 / 计划 / 呈现 / 工程区或草稿发生变化，或目标指纹变化，须重新准备。后台结果更新本身不作输入变化。
3. **写入与发布。** 复用 `prepare_write` / `write_prepared` 的序列化快照、目标复核与 staged write。确认后提交同一份已准备字节。写入成功才一次性发布活动标识、路径、文件能力和各域保存基线。初始化属于一次项目保存事务，不作为可撤销的建模编辑。保持原有建模历史和草稿。对象图与实际执行配置相同的活动会话继续按既有规则保有结果资格，关闭重开后仍为 Missing。
4. **取消、失败与重试。** 取消、分配失败、校验失败、目标变化或 IO 失败都不发布标识、切换路径或推进保存基线。写失败复用现有 staged write 恢复。Windows 替换与回滚均失败时显示原恢复错误和备份路径，待确认文件状态后重新准备，内存仍为原状态。若写入成功后进程退出，重开以实际磁盘文件为准。再次执行启用时，已启用文件直接沿用保存的标识。

普通保存和另存继续保留已启用身份区。新 v4 writer 需额外检查目标能力移除，拒绝用未启用的内容覆写已初始化目标，覆盖或升级确认不能绕过。已启用内容的普通另存遵守现有覆盖流程，写出源工程的身份；当目标已有不同的身份记录时，确认中明确目标旧引用可能失效。保持现有文件系统并发边界，确认和 staged write 不提供跨进程锁。 [现有写入准备与提交](../../../crates/rf-store/src/project_v4/file_io.rs) · [Studio 确认入口](../../../apps/radishflow-studio/src/studio_gui_shell/project_save.rs) · [Windows 失败恢复](../project-lifecycle-storage.md#windows-staged-write-失败恢复)

## 旧读者、写入器和协议

| 入口 | 候选兼容规则 |
| --- | --- |
| 新 Studio 打开 v1–v3 或未启用的 v4 | 沿原有兼容规则读入，无身份区可继续编辑和普通保存。已知 v4 和身份 v1 按严格 DTO 恢复；合法未知身份能力版本整份只读，已知 v1 的坏数据报格式错误。 |
| 支持 v4、早于本功能的 Studio / v4 store | 在严格解码新字段前发现未知必需能力，保留整份原 JSON 并只读。拒绝计算、编辑、序列化、保存、另存和用该 writer 覆盖已初始化目标。发布前须用冻结旧版本实测。 |
| 仅支持 v1–v3 的 Studio 及 CLI v1–v3 | 沿各入口的外层版本规则拒绝 v4，不做隐式降级或写回。冻结旧版 Studio 的已有目标覆盖拒绝需独立核实。 |
| 当前 CLI v4–v7 协议 | 继续按协议能力表限制，身份 v1 视作未支持。只读查询沿原契约仅给安全元数据与原因，执行在任何步骤或资源装载前拒绝。Studio 与 CLI v7 当前共用 `FlowPlanSupport::Mixed`，实现时须把对象身份支持与求解计划支持分别传入，避免给旧协议无意开放。 |
| 低层 legacy `write_project_file` | 现有函数只验证待写 v1/v2 内容，随后允许替换目标。历史库若由调用者直接传入目标路径，不能宣称具备上述 Studio 保护。本批建议给新构建的该项目写入入口加目标检查，拒绝覆盖 v4 及更新版本，保持正常 v1/v2 写入。 |

启用后本片不提供降级保存。需要旧版本继续编辑或运行时，可在迁移时保留未启用的原文件，副本的后续修改由各自路径管理。兼容验证分别覆盖 Studio、CLI 和上表列出的项目 writer。 [v4 能力探测](../../../crates/rf-store/src/project_v4/mod.rs) · [CLI 版本分派](../../../apps/radishflow-studio/src/headless/v3/mod.rs) · [legacy writer](../../../crates/rf-store/src/json.rs)

## 实施验收与评审点

| 验收 | 最小证据 |
| --- | --- |
| 严格存储 | 完整 v4 与空工程往返，标识排序稳定。缺能力、缺区、重复、孤儿、非法 UUID、已知坏字段拒绝。未来正版本保持原字节只读。已有项目字段和计划往返对照。 |
| 迁移与恢复 | 以 v1、v2、含工程区的 v3、已有计划的 v4 分别验证普通保存无隐式升级、显式初始化原位 / 新副本、实际目标变化、取消、IO 失败与 Windows 恢复。检查原件字节、路径、修订、草稿和保存基线。重复启用无重新分配。 |
| 事务与引用 | 创建、删除、撤销、重做、保存重开后重用 ID、同 ID 分叉独立新建、移动、另存失败、两份未启用副本分别迁移。验证只有成功保存的当前对象可以新复制引用，保留的草稿和运行结果资格符合原规则。 |
| 冻结旧版 | 用 `ee5f8785` 的 v4 reader / writer 对新样本验证只读、原字节、序列化拒绝和既有目标覆盖拒绝。用 v4 接入前的 `7b4fb934` Studio 验证打开与覆盖拒绝。新构建的现有 CLI v1–v7 分别按上表验证，检查原文件和 sidecar 无写入。报告区分独立旧库测试、真实 CLI 进程与原生 GUI。 |

请评审三项选择。第一，采用 v4 必需能力与独立身份区。第二，所有首次启用通过一次明确的初始化保存，默认保留旧版可用的原文件。第三，已启用文件在既有 CLI v4–v7 中仅能按原只读入口检查，并补齐新构建 legacy writer 的目标保护。方案确认后，拟按 codec 与旧读者保护、初始化事务与恢复、Studio 引用接线顺序推进。上述均为实施验收计划。
